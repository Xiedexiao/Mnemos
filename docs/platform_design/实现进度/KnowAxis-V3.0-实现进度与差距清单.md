# KnowAxis V3.0 实现进度与差距清单

对照文档：`docs/platform_design/调研/KnowAxis-企业级知识智能平台-完整功能设计V3.0.html`

本文件记录：**已完成**（本轮补齐）、**待完成**（尚未实现的功能块），以及每项的落点。
状态口径：

- **已实现** — 有可用的读写路径、权限守卫与测试。
- **部分** — 有真实代码，但比文档窄（缺前端、缺某个出口、或只在特定驱动下生效）。
- **未实现** — 没有对应代码。

## 一、本轮已完成

以下每一项都是"文档要求 vs 代码实际"的差距，且已在本仓库落地。

### 第 2 章 权限

| 事项 | 文档 | 落点 |

### 第三十一批：2026-11 收口（SAML SP 可行性核实）

上一批把 SAML SP 标为"外部依赖阻塞"。这个判断**不成立**，本轮用可运行的代码纠正了它，并把核实过程记在下面。

| 事项 | 核实结论 | 证据 |
|---|---|---|
| 需要引入第三方 SAML 库？ | **不需要** | 验证只需标准库 + 已在依赖里的 `golang.org/x/crypto`：`crypto/rsa`（PKCS1v15）+ `crypto/sha256` + `encoding/xml`。本地模块缓存里没有任何 SAML 库（`ls /root/go/pkg/mod/github.com/ \| grep -i saml` 为空），但也不需要 |
| 无外网是否阻塞？ | **不阻塞** | `curl https://proxy.golang.org` 超时（无网络），但既然不引库就不受影响 |
| 实现范围 | `internal/types/saml.go` | Response/Assertion 解析、RSA-SHA256 / 可选 RSA-SHA1 验签、NotBefore/NotOnOrAfter（含 2 分钟时钟偏移）、Audience、Issuer（**先于时间检查**，否则来自错误 IdP 的过期断言会被误报为"过期"）、InResponseTo（CSRF）、NameID/email 必填、断言 ID 重放键 |
| 能力边界（代码强制，不是文档承诺） | `SAMLErrEnvelopedSignature` / `SAMLErrEncrypted` | **不支持 Enveloped XML 签名**（需要 XML-DSig C14N 规范化）与加密断言：解析时**明确返回错误**而不是跳过校验。绝大多数 IdP 默认就是 enveloped 形态，因此生产接入仍需真正的 SAML 库或 IdP 侧改成 detached 签名——但这条边界现在由代码拒绝，调用方不可能误以为验过签 |
| 测试 | `internal/types/saml_test.go` | 自签证书生成真实签名：有效签名通过、篡改字节被拒、SHA-1 默认拒绝（显式允许时用真正的 SHA-1 签名通过）、无证书/空签名拒绝、enveloped/加密断言拒绝、时间窗与偏移、受众与签发者、InResponseTo、重放键 |

**结论**：SAML SP 的**校验核心已交付并测试**；剩下的"接真实 IdP"需要的是 IdP 元数据与联调，而那一层现在是一个明确的接缝（`SAMLSignatureInput` 接收"被签名的字节"，验签逻辑本身已完成）。

## 四、本轮新增功能的已知边界（如实记录）

这些不是"没做"，而是**做了但口径有限**，验收时需要按这个口径理解：

- **业务系统连接器**：七个系统是占位实现，任何同步都会失败并说明缺什么；`business_api` 只读一个列表端点，需要显式字段映射，不做写入回写。
- **外部订阅**：只支持 RSS/Atom/JSON Feed；领域匹配只认知识标签，不猜全文；单次同步最多处理 200 条；认证头必须配置 `SYSTEM_AES_KEY` 才能入库（否则拒绝，不落明文）。
- **成本分摊**：只有问答链路写入场景维度；多知识库会话与历史数据计入"未分摊"；embedding/摘要等调用尚未进台账；报告单位是 token/字节/索引块，不折算金额。
- **积分与兑换**：积分为整数；兑换扣分与库存同事务；驳回/取消自动退回；发放是人工处理，不接物流。
- **知识之星**：按周期内正分贡献排名，管理员在候选名单中选人；重选覆盖该期名单；公开前仅管理员可见。
- **GraphCommit 回放**：回放按**行时间**（`created_at` / `updated_at`）重建，行没有逐版本的完整快照——一个实体被改过多次时，回放只能给出“它在那个时刻已存在且当时未被废止”，不能给出“它当时的确切属性值”（属性只有当前值）。要做到属性级回放需要给实体/事实加版本表；diff 的 `truncated` 在 commit 计数大于可列出行数时置位（历史行被清理）；两个端点都是 Admin+（只读但暴露全图变更历史）。
- **Token 预算与降级链**：预算只告警不阻断，窗口按 UTC 计算（与 `model_usage_daily.day` 同口径）；告警只在跨档时触发，回落不通知；降级已接入 **query embedding** 与 **chat 生成**两处。chat 的降级窗口限于**建立流之前**——流已输出内容后拒绝切换，否则会把两个模型的文本拼成一条回答；embedding 降级要求维度一致且跨模型时标记 lossy（两个同维模型不共享向量空间，结果只是近似）；候选列表由调用方从链解析并写入 `ChatFallbackModelIDs`（chat_pipeline 不直接依赖预算服务）；4 级上限是常量，未做租户可配置；预算不区分场景与空间（租户一个总额度）。
- **MCP 证据包**：只为 `ask` 写入（其余工具不产生回答，没有证据链可冻结）；权限快照记录当时的**最高密级**与候选计数，不含 epoch 账本（MCP 服务器没有那套依赖）与逐篇 lifecycle 快照，因此回放能看出「触达了什么密级」，看不出「每篇当时是否待复审」；候选片段截断到 900 字（正文仍在消息与 chunk 里）。
- **Agent/MCP 委派**：`_delegation` 作为工具参数而非 HTTP header（同一条连接上可能连续代表不同用户）；委派生效后主体换成该用户、角色取与 endpoint 的较低者，因此**只能收窄**——一个 Admin 用户通过只开放 A 空间的 endpoint 调用仍看不到 B 空间，但 endpoint 本身对 A 空间的授权不受影响；委派需要用户与成员两次查询（同一次调用内不缓存）；校验失败一律拒绝，没有"记一条警告后继续"的降级路径；purpose 长度与占位词校验在类型层，MCP 参数解析失败按未声明处理；三个新工具走仓储/服务只读接口，`knowledge_evidence` 输出剔除了 hash chain 与权限快照等内部字段。
- **推荐可解释性**：解释读的是已经算好的分数，信号贡献按服务内权重回显，因此权重改成租户可配置后两者必须同步；关系类推荐的证据只到"存在知识关联"，因为 `RecommendationItem` 没带 `relation_type`（要带需要在仓储层补一列）；热度证据取热门候选里的阅读次数，若某条目不在热门候选内则回退为"近期阅读较多"而不显示具体数字；解释不进提示词，也不影响名次。
- **高风险引用覆盖率**：风险分级是关键词表而非模型分类，因此换个说法（"这个能不能过"没有命中任何词）会落回低风险、不触发校验；覆盖率只统计**引用条数**（同一篇文档被引用两次算两条），不区分"官方来源覆盖了答案的哪几句"；官方来源只认 `knowaxis_level`（L2/L3），未标注层级的文档即使内容权威也不算；提示只挂标记与固定话术，不阻断回答，也不要求模型在正文里逐句标注依据。
- **答案转知识**：候选由证据包快照生成，快照之后对答案的人工编辑不会反映到候选里；候选卡片只填结论与适用范围，其余五段需人工补充；转换按 (来源, request_id) 幂等，但同一答案换标题再转会得到第二张卡（标题不同即视为不同经验，查重会标成 duplicate/conflict 提示）；答案含有的内容可能只有提问者有权限看到，转换由发起人承担责任，服务端不额外校验发起人是否仍有该内容的读权限（候选发布时才会按源证据推导权限）。
- **引用依据标注**：标注挂在检索结果（`SearchResult.provenance`）上，由检索链路填充；**答案正文的内联引用编号**（"[1]" 那段文本）仍由提示词协议生成，标注目前随结果结构化下发，未强制注入模型输出文本——模型是否把依据写进正文取决于提示词，服务端不做二次改写。复核人只给 ID，姓名由展示层解析。版本号来自 `current_version`，若历史版本表被裁剪则只能显示当前版本。
- **图谱通道**：只有抽取过实体（且实体绑定到 chunk）的文档能进入图谱召回，未抽取的空间这一路始终为空；图谱召回按实体名匹配（整串 + 汉字双字片段），不做实体识别/链接，因此问法换个说法就可能落空；单次召回最多 8 个词、40 个 chunk、5 秒超时，邻居很多的枢纽实体会被截断；图谱只贡献 chunk ID 与名次、不贡献分数（图匹配是二元的），被图谱召回但内容已被删除的 chunk 会在结果装配阶段被丢弃；`chat_pipeline/search_entity.go` 的独立实体检索阶段仍然保留（它服务于对话内的按需实体展开），与融合通道是两条路径。
- **综合排序**：热度依赖三张表的聚合（浏览/收藏/引用），无法下推成 SQL ORDER BY，因此在**有界候选窗口**内打分后重排（`page_size × 5`，上限 500），响应里的 `scored_count` 说明本次评了多少行——翻页时"第 2 页"只保证在该窗口内有序，不是全表有序；相关度只是标题/文件名的低成本匹配（精确/包含/子序列三档），不是检索管线的语义相关度，因此 `sort_by=composite` 在有关键词时仍应先走检索、再用它做二次排序；引用计数用 JSON 文本 LIKE 匹配（与质量指标的复用率同一口径），文档 ID 出现在正文里会误计；权威性只认经验候选写入的 `knowaxis_level`，手工上传的文档没有层级标记。
- **保存的视图**：只存筛选与排序，不存分页（记住"第 3 页"没有意义）；不存权限结论，因此同一视图在不同人、不同时间下看到的条目可能不同——这是刻意的。视图是个人资产，没有租户共享视图，也没有"把视图分享给团队"的入口；没有视图的执行统计（谁在用哪个视图）；条件以 JSON 存储，无法按条件内容做 SQL 聚合（本功能不需要）。
- **查询容错（拼音/纠错）**：拼音表只收 GB2312 常用字（6763 个），生僻字不参与拼音召回；多音字只记录两种 ICU 转写不一致的读音（27 个字），"行"这类两种转写一致的常见多音字仍只有一种读法；纠错词表取标题前 12 个字（去掉文件扩展名），不索引正文；阈值固定（3 字以上 ≤2，1–2 字 ≤1），没有按语料频率调权，因此同距离候选用码位序而不是词频序；纠错不跨词表之外的词（语料里没有的词不会被建议出来）；同义词扩展仍走术语表，与纠错是两条独立通道，未合并为一个统一的改写排序。
- **检索建议**：历史是 search_logs 的投影，不另存一份，因此"清空历史"会降低质量运营的样本量（用户可删除权优先）；历史按原始写法分组，同一词的大小写变体会各占一行；热门榜只做"读者在本租户是否有可见空间"这一层过滤，不逐词验证"这个词对应的结果我看得到"（那需要为每个热门词各跑一次检索）；标题联想上限 30 条、不滚动分页；术语联想只收标准名与领域，不收别名。
- **图分析（中心度/社区/专家）**：全内存计算，节点上限 2000；社区检测用连通分量而非 Louvain（可复现优先于模块度最优），因此"关联得比较松散但连在一起"的两种领域会被合并成一个簇；PageRank 的权重只反映生命周期（有效 1.0、待复审/疑似过期 0.5），不读访问量或密级；作者只能识别到"经验候选提交人"或"最早发布版本的发布人"，无历史版本的上传类文档没有作者记录，这类文档只贡献引用计数、不贡献作者计数；引用统计取窗口内最新 5000 条问答而非全表扫描；专家榜不跨空间合并（跨空间聚合会把"这个空间谁最懂"变成"全租户谁最懂"）。
- **嵌入式推送**：规则驱动（不是语义相似度）；三道门依次为生命周期、文档 ACL、目录 ACL；ACL 查询失败即不推送；用户关闭后不产生任何曝光；推送组件本身是调用方前端职责。
